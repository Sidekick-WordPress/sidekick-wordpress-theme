# Sidekick WordPress Theme Architecture

This document outlines the architectural decisions, development workflow, and styling philosophy for the Sidekick WordPress Theme. This theme embraces the Full Site Editing (FSE) paradigm, leveraging `theme.json` as the primary configuration hub while maintaining a modern, streamlined SCSS build process for granular control.

---

## The Core Philosophy: The "CSS Variable Bridge"

In modern FSE theme development, **`theme.json` is the source of truth**. Hardcoding design decisions (like colors, base typography, and max-widths) in CSS fights the block layout engine and breaks the user's ability to use the Site Editor.

Instead, we use a hybrid approach:
1. Define colors, typography, and spacing in `theme.json`.
2. WordPress automatically generates CSS custom properties (e.g., `var(--wp--preset--color--primary)`).
3. We consume those native CSS variables inside our SCSS to style custom elements, keeping the compiled code perfectly synchronized with the database-driven Site Editor.

---

## Build Process & Asset Management

We use `@wordpress/scripts` to compile SCSS without the overhead of maintaining a custom Webpack configuration.

### Getting Started

```bash
# Install dependencies
npm install

# Run the dev compiler (watches for changes, maps sources)
npm run start

# Build for production (minifies CSS)
npm run build
```

### File Structure & Routing
To avoid unnecessary dummy JavaScript files while keeping our build process clean, we point Webpack directly at our SCSS file:

* **`/styles/style.scss`**: The master SCSS entry point.
* **`/build/style-style.scss.css`**: The compiled CSS output.
* **`/build/style.scss.asset.php`**: Auto-generated by Webpack. We use this file in `functions.php` to enqueue the stylesheet. It automatically generates a version hash based on file contents, providing **automatic cache-busting** every time the SCSS is recompiled.

### The Root `style.css`
The `style.css` file located in the root directory contains **only** the WordPress theme declaration comment block. It acts purely as the theme's ID card for WordPress core. **Do not write CSS in the root file.** All custom styling must happen in the `/styles/` directory.

## SCSS Strategy: What Goes Where?

With FSE handling the heavy lifting, our SCSS is significantly leaner.

### 1. The Reset (`_reset.scss`)
Do not use heavy, traditional normalizers that apply aggressive layout rules to the `body`, `main`, or typographical elements. FSE handles this. Our reset is strictly limited to:
* Global `box-sizing: border-box`.
* Browser-specific scrollbar styling (Webkit/Firefox).
* Micro-typographic text-level semantics (`sub`, `sup`, `abbr`).
* Basic table border-collapse rules (relying on `theme.json` variables for colors/padding).

### 2. Variables & Media Queries (`_variables.scss` & `_functions.scss`)
Because CSS custom properties cannot currently be used inside `@media` declarations, **breakpoints are the only design values stored as SCSS variables.**

We use a custom `em()` function that allows developers to write breakpoints in pixels, which the compiler then translates to accessible `em` units for robust, zoom-friendly responsive design.

```scss
$breakpointDesktop: em(1008); // Developer inputs 1008px, compiler outputs 63em
```

## Working with Core Blocks

We avoid targeting deep, core block DOM structures (like `.wp-block-navigation__container > ul > li`) to future-proof the theme against WordPress core HTML changes.

### Styling Blocks Safely
1. **Global Block Styles:** Base styles (like making all menus bold and uppercase) are defined directly in the `styles.blocks` object within `theme.json`.
2. **Native FSE Settings:** Structural behaviors, like making the header Sticky, are handled natively in the block markup (`"position":{"type":"sticky"}`).
3. **The Block Styles API:** For distinct visual variations (e.g., "Pill" shaped navigation links), we register a custom block style in `functions.php`. This gives the user a toggle in the editor sidebar, appending a clean class (e.g., `.is-style-pill-links`) that we can safely target with our SCSS.

## The Master Layout Switch: `blockGap`

The vertical rhythm and flex spacing of the entire theme are governed by the `blockGap` property in `theme.json`.

```json
"spacing": {
  "blockGap": "1.5rem"
}
```
This single declaration eliminates the need for complex SCSS margin resets (the "lobotomized owl" selector). It acts as `margin-top` for stacked flow layouts and `gap` for side-by-side flex layouts, dynamically adapting to the user's block composition.
